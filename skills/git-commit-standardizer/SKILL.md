# Git Commit Standardizer

按下面流程执行，不跳步。

## 1. 收集约束

1. 先读取仓库约束文件，优先级如下：`AGENTS.md` > `CONTRIBUTING*` > `README*`。
2. 再查看最近提交风格：`git log --oneline -n 20`。
3. 若仓库已有明确格式，严格遵守仓库格式；仅当仓库无约定时，使用本 skill 的通用规则。

## 2. 收集变更

1. 优先基于暂存区生成提交：`git diff --cached --name-only`。
2. 若暂存区为空，再查看工作区：`git diff --name-only`。
3. 阅读变更内容时优先用：`git diff --cached`；若无暂存变更则用 `git diff`。
4. 用 `scripts/suggest_commit_scope.py` 推断推荐 scope，并把输出作为候选，不要盲信。

## 3. 生成提交信息

遵循以下规则：

1. 标题保持单行、简短、可扫描，不写句号结尾。
2. 默认格式：`scope: summary`。
3. `scope` 优先取受影响最多的模块或目录。
4. `summary` 用动词开头，描述“做了什么”，不要描述“为什么执行命令”。
5. 避免空泛词：`update`、`fix bug`、`misc changes`。

仓库无约定时，使用这些通用长度建议：

1. 标题建议 <= 72 字符。
2. 如需正文，正文每行建议 <= 72 字符，并说明关键影响或兼容性。

## 4. 提供候选并确认

1. 先给出 2-3 个候选标题，按“最推荐 -> 备选”排序。
2. 如果用户未指定，默认采用最推荐标题。
3. 提交前明确告知将执行的命令：`git commit -m "<subject>"`。

## 5. 执行与回显

1. 执行非交互式命令，避免打开编辑器。
2. 执行后回显核心结果：提交哈希、标题、变更文件数量。
3. 若提交失败，输出可执行修复步骤并重试。

## 6. 拆分提交策略

当一次改动包含多个主题时，按下列顺序处理：

1. 先把“功能改动”和“重构/格式化改动”分离。
2. 先提交风险低、边界清晰的改动。
3. 每个提交只表达一个主要意图。

## 7. 冲突与不确定性处理

1. 当仓库规范与通用规则冲突时，始终服从仓库规范。
2. 当改动意图不清晰时，先基于 diff 产出最小可行标题，并明确假设。
3. 不编造未发生的改动，不把测试结果写进标题。
